# Почему atlas устроен так — анализ GRACE и codescribe

Документ объясняет, из чего вырос atlas, какие идеи GRACE сохранены, от каких отказались и почему.
Источники (сентябрь 2026): GRACE 4.2.1 (osovv/grace-marketplace — 15 скиллов, CLI `src/`, журнал решений автора
`.vvoc/specs/grace4-artifact-model/design-context.xml`, CHANGELOG 1.3→4.2.1, issues/PR), GRACE 3.11 (`grace-explainer`),
codescribe 1.0.0 (производная владельца от GRACE 3.x) и его применение в 6 проектах, код и документы AI.UI,
официальная документация Claude Code (memory, rules, skills, hooks, sub-agents) и Codex (AGENTS.md).

## 1. Что такое GRACE

GRACE — Graph-RAG Anchored Code Engineering: методология разработки с LLM на четырёх опорах —
граф знаний о модулях (XML), контракты модулей и функций в коде, семантические блоки `START_BLOCK_X` / `END_BLOCK_X`
(~500 токенов), план верификации с лог-маркерами `[Module][fn][BLOCK]`.

| Версия | Дата | Что добавилось |
|---|---|---|
| 1.x | 17–20.02.2026 | `docs/*.xml` + разметка в коде + скиллы; ревьюер ещё из чужого плагина |
| 3.0–3.11 | 03–04.2026 | verification-plan, operational-packets, Bun CLI `grace lint`, ROLE/MAP_MODE, query-слой, autonomy gate |
| 4.0–4.2.1 | 06–09.2026 | каталог `.grace/` со строгой XML-грамматикой; жизненный цикл изменений spec → plan → execute → archive; assertions, scopes, recovery, run-evidence |

Цена GRACE 4: 15 скиллов ≈ 17K токенов инструкций; CLI — 8 845 строк кода, 5 484 строк тестов, 4 353 строк скриптов
релиза; ≈ 148 кодов диагностики; изменение одного модуля затрагивает ≈ 12 файлов `.grace` плюс код и тест.

Вектор развития — от «помочь понять код» к «управлять долгими автономными прогонами». Самый подробный внешний
отзыв — issues #50–#56 (все открыты): монолитный `graph/main.xml` конфликтует при каждом merge; ручной перенос в архив
дал 2 дефекта из 7; за 115-часовой прогон 39 ч 31 мин ушли на ожидание «continue»; 40% времени гейтов — повтор уже
зелёных команд. Боль — в процессном весе, а не в идее карты.

## 2. Мотивы автора

Явная формулировка (GRACE 3.11): LLM теряет контекст между сессиями — не знает, какие есть модули и как они связаны;
дублирует или противоречит существующему коду; не может трассировать баги; дрейфует от архитектуры.

За каждым механизмом стоит своя теория. Разбор:

- **Граф знаний — «карта вместо чтения кода».** Верно, и это главная ценность GRACE. Но граф хранит в основном
  выводимое (экспорты, зависимости по импортам) — именно это гниёт первым и требует CLI для контроля паритета.
- **Уникальные XML-теги, «closing-tag polysemy», «semantic accumulator».** Гипотеза о механике внимания
  трансформера: `</M-CONFIG>` будто бы «реактивирует» смысл блока, а `</Module>` заставляет модель искать, что закрыто.
  Ни одного замера у автора нет. Проверяемая польза только одна — уникальный ID находится одним grep. Её atlas сохраняет
  (ID в заголовках Markdown), от XML отказывается: теги удваивают токены, плохо читаются в diff и провоцируют конфликты.
- **Блоки ~500 токенов.** Наследие vector-RAG («Graph-**RAG**»): граница чанка определяла, что попадёт в выдачу.
  Современный агент ищет сам (grep → чтение диапазона строк), границы чанков ему не нужны. Цена — шум в каждом файле.
  Сохраняется только якорь «внутрь длинной функции» — существующий разделитель раздела.
- **Контракт до кода, PCAM, top-down synthesis.** Сдерживает генерацию нового кода слабой моделью. Для уже написанного
  кода контракт — просто резюме, которое надо синхронизировать при каждой правке.
- **Лог-маркеры.** Навигация «строка лога → место в коде». Верно; atlas сохраняет навигацию, но не навязывает формат:
  если логи — обычные русские сообщения, достаточно grep статического фрагмента.
- **Verification, assertions, scopes, immutability.** Доказуемая автономия многочасовых прогонов. Для понимания
  проекта ценна только часть «как проверить модуль» — она переходит в карточку.
- **CLI, fail-closed.** «LLM сама не синхронизирует». Мотив верный, но рассинхрон порождает дублирование фактов;
  CLI лечит симптом. atlas убирает причину: один факт — одно место.

## 3. Практика: codescribe в 6 проектах владельца

codescribe — производная от GRACE ~3.5: 7 артефактов `docs/*.xml`, полная разметка в коде, 2 скилла
(document/update), без CLI.

- **Объём.** parser-ops ≈ 290 КБ XML (граф 94 КБ, план 78 КБ, верификация 82 КБ), VP ≈ 178 КБ. AGENTS.md велит читать
  граф → план → требования → … — это ≈ 45–70K+ токенов до первого файла кода.
- **Налог в коде.** 344 (parser-ops) и 326 (VP) размеченных файлов; разметка занимает 7–55% строк файла
  (VP `auth.ts` — 55%). Налог платится при каждом чтении файла в каждой сессии.
- **Синхронизация исправна.** Слой отстаёт на 1–6 коммитов; граф parser-ops переписывался 35 раз с 1 августа.
  Значит, проблема не в дисциплине, а в **цене каждой синхронизации**: сотни КБ XML плюс разметка в сотнях файлов.
- **Корень.** Один факт лежит в 3–5 местах: граф, план, MODULE_CONTRACT, MODULE_MAP, верификация, CHANGE_SUMMARY.

## 4. Поэлементный разбор

| Элемент GRACE | Ценность для «что/где/как» | Цена | Решение atlas |
|---|---|---|---|
| Модули: назначение + путь | высокая | средняя | таблица L0 с входными файлами и процессом |
| `fn-*`/`type-*`, MODULE_MAP | низкая — выводится grep/LSP | дрейф, нужен CLI-паритет | не хранить |
| DEPENDS/CrossLink по импортам | низкая — выводится из import | дрейф | только неимпортные связи |
| DF-* потоки | высокая для «как», но в GRACE — голый список модулей | — | трассы `путь:символ` с процессами, асинхронностью, режимами |
| MODULE_CONTRACT | средняя | 8–15 строк на файл, дубль графа | существующая шапка файла; карточка её не повторяет |
| Контракты функций | средняя: невыводим только SIDE_EFFECTS | 7 строк на каждый export | «Состояние и побочки» в карточке + карта данных L0 |
| START/END_BLOCK | низкая | 7–55% шума | якорь `файл:символ#«раздел»` на существующих разделителях |
| CHANGE_SUMMARY, VERSION | низкая — git log/blame | конфликты merge | «почему» — inline-комментарий со ссылкой на решение |
| Лог-маркеры | высокая | низкая | раздел «Логи» в L0: где, формат, как искать источник |
| V-M-* | средняя — «как проверить» | высокая | «Проверка» в карточке: тест-кейсы, сигналы, сборка |
| 5 context-артефактов | tech/deploy — средняя | 5 файлов | L0 «Документы» + граница «ТЗ ↔ код» |
| Change lifecycle | для понимания — ноль | очень высокая | нет; модуль = единица write-scope для параллельных исполнителей |
| Public/private split | высокая — держит общие доки маленькими | — | правило: L0 — граница, карточка — модуль, код — детали |
| XML | не доказана | ×1.3–2 токенов, плохие diff | Markdown с уникальными ID |
| Bun CLI | принуждение | зависимость, баги на Windows | проверки агентом через Grep/Glob/git |

## 5. Чего в GRACE нет, а агенту нужно (на примере AI.UI)

1. **Процессы и режимы.** Хаб в Docker работает в режиме `docker` (роутер и PeerStore, SDK-runtime не грузит);
   agent-host в контейнере агента — `sidecar` с `AGENT_ID`; есть dev-sidecar и inprocess. Одно слово «sidecar» —
   два разных режима. Граф GRACE описывает только статику кода.
2. **Карта данных.** Путь → кто пишет → кто читает → владелец. Скрытые связи идут через общие файлы и тома
   (роутер хаба читает session.json агента прямо с общего тома).
3. **Рецепты изменений** из реальных совместных коммитов: «новый маршрут = api.ts + useAgentsApi.ts + types.ts
   [+ router.ts, + регекс путей в middleware]».
4. **Тексты для модели как класс связей.** Промпты, описания MCP-инструментов, форматы писем, файлы правил для
   хостируемых агентов. Поведение поменяли, текст нет — агенты ломаются молча.
5. **Омонимы.** «Сессия» в AI.UI — четыре разных сущности. grep находит слово, но не смысл.
6. **Карта документов.** ТЗ — намерение и частично устарел; BACKLOG и TEST-PLAN — искать grep по строке таблицы,
   а не читать целиком (вместе это 60–70K токенов — та же цена, что у codescribe).
7. **«Не читать».** В AI.UI 671 вендорный файл UI и 130 файлов бандлов плагинов — без явного списка агент тратит
   на них вызовы.
8. **Доставка до субагентов.** Встроенные Explore и Plan не получают CLAUDE.md и правила — а поиск по правилам
   владельца идёт именно через субагентов.

## 6. Что atlas берёт у GRACE

grep-уникальные ID; разделение «граница в общем индексе / детали локально»; навигацию «лог → код»; «как проверить»
как часть знания о модуле; обновление по git-diff (из codescribe); семантическое именование; гейт одобрения границ
модулей; политику моделей (быстрые — сбор фактов, сильная — авторство); правила ответа `grace-ask` — ссылаться на
проверенный в этой сессии якорь, отделять текущее состояние от планов, называть неуверенность и следующий поиск.

## 7. Решения atlas и почему

- **Только невыводимое (P1).** Всё выводимое одним вызовом агент получит быстрее и точнее, чем прочтёт в доке, —
  и оно никогда не устареет. Невыводимое (смысл, причины, режимы, неявные связи) — то, ради чего карта вообще нужна.
- **Один факт — одно место (P2).** Устраняет причину дорогой синхронизации, а не лечит её инструментом.
- **Доставка по каналу (P3).** L0 через `@AGENTS.md` — ноль вызовов на ориентацию, в том числе для кастомных
  субагентов. Карточка через `.claude/rules` с `paths` приходит при первом Read файла модуля: к этому моменту агент
  уже нашёл файл, поэтому карточка — страховка при правке (инварианты, «что менять вместе», побочки), а навигацию
  («что/где») несёт L0.
- **Бюджеты в токенах (P4).** Раздувание убило лёгкость GRACE и codescribe; бюджет — единственная защита, которая
  не требует инструментов. Строки — плохая единица для русских таблиц: замер на AI.UI — L0 в 12,7 тыс. символов
  (123 строки) добавил к стартовому контексту свежей сессии ≈ 6,8K токенов (9,6K → 16,4K), около 2 символов на токен.
- **Свежесть по якорям (P6).** В AI.UI ≈ 28 коммитов в день; признак «были коммиты в файлах модуля» пометил бы
  устаревшими почти все карточки всегда. Карточка устаревает, только если изменилось то, на что она ссылается.
- **Write-through (P8).** Правка карточки — часть заказанного изменения и только при смене якоря, инварианта
  или связи. Отдельных автономных «волн документирования» нет — это согласуется с правилом владельца «только по команде».
- **Существующие ID (§11 метода).** Решения — `BACKLOG #NN`, проверки — T-кейсы. Новых реестров (V-M-*, INV-*)
  не заводится: в коде AI.UI уже 32 ссылки `BACKLOG #NN` в 25 файлах.

## 8. Риски и защиты

| Риск | Защита |
|---|---|
| Карточки дрейфуют | мало фактов, только невыводимые; свежесть по якорям; C3/C4 ловят сломанные ссылки |
| Карточки раздуваются | бюджет 6 000 символов; «одна ловушка вошла — одна вышла»; atlas-sync показывает размеры |
| Неверная нарезка | гейт одобрения; границы — по импортам и совместным коммитам, а не по папкам |
| Горячие общие файлы | вынесены в L0 «Общие файлы», без владельца |
| Битый glob / frontmatter | одинарные кавычки, каталоги вместо скобок Nuxt; C1 и C5; проверка доставки в init |
| Карточки грузятся слишком часто | подмешиваются один раз за сессию на модуль; ≈ 2K токенов каждая |
| Субагенты без карты | atlas-scout; шаблон делегирования в протоколе L0 |
| Другие агенты (Codex) | L0 — это AGENTS.md; карточки и трассы — обычный Markdown по ссылкам из L0 |

## 9. Как доказывается польза

A/B-замер на AI.UI: 13 вопросов пяти типов («где», «как», «что затронет», «лог → код», план изменения, ловушка
устаревшей доки, контроль по вендорному коду) заморожены до построения слоя. Каждый прогон — свежая headless-сессия
atlas-scout на Sonnet; плечо A без слоя, плечо B со слоем, по 2 прогона на вопрос. Метрики — вызовы инструментов,
токены, время, полнота фактов эталона, галлюцинации, ловушка. Оценка слепая, силами основной модели.
Критерий успеха заранее: медиана вызовов и токенов B ≤ 0.7 × A при полноте не ниже A − 5 п.п.

**Результат 24.09.2026** (подробно — `EVAL-AI-UI-2026-09-24.md`): медиана вызовов 17 → 5 (0.29×), токенов
179K → 79K (0.44×), времени 54 → 27 с; полнота 80.8% → 80.7%; галлюцинации 1.1% → 0.3% ссылок; ловушку прошли оба плеча.
Выигрыш сосредоточен в «как работает» (трассы: ×15–23 по токенам и вызовам); на «что затронет» и плане изменения
выигрыша нет, полнота ниже — агент доверяет рецептам L0. Ошибки карты переходят в ответы, поэтому точность трасс
и рецептов важнее их количества.

## 10. Что сознательно не делается

- **Миграция codescribe-проектов** — позже и отдельно: засеять модули, назначения и потоки из `docs/*.xml`, сверить с
  кодом; удалять XML и разметку — только по команде владельца.
- **Хуки** (напоминание обновить карточку после правки, отчёт о свежести при старте сессии) — требуют скриптов;
  вернуться, если write-through на практике будет пропускаться.
- **Проверочный скрипт** — владелец выбрал проверки агентом; вернуться, если C1–C6 станут дорогими.
- **Процессный слой GRACE** (spec/plan/assertions/archive) — у проекта свой процесс: BACKLOG, TEST-PLAN, git.
